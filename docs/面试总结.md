# C++ 多线程文件扫描器面试总结

## 1. 30 秒项目介绍

这是一个基于 C++17 的 Windows 多线程文件扫描器。项目使用 `std::filesystem` 递归遍历目录，使用自定义有界线程池处理文件元数据，支持扩展名和大小过滤、错误日志、CSV 导出、Win32 GUI 和 1/2/4/8 线程性能对比。CLI、GUI 和测试脚本共享同一个扫描核心，项目通过 CMake/Ninja 构建，并使用 PowerShell smoke test 验证边界场景。

## 2. 项目亮点

1. 将线程池从业务代码中独立出来，形成可复用的生产者-消费者模块。
2. 使用有界任务队列提供背压，避免大目录下任务无限堆积。
3. 使用 `std::error_code` 处理文件系统可恢复错误，使用异常处理配置和初始化失败。
4. 使用互斥锁保护扩展名统计、元数据和日志文件，使用原子变量保存高频计数。
5. CLI 和 GUI 复用扫描引擎，避免两套业务逻辑产生行为差异。
6. 通过 smoke test 验证线程一致性、空目录、非法目录、CSV、日志、参数边界和 GUI 生命周期。

## 3. 推荐讲解顺序

```text
命令行/GUI 输入
→ ScanOptions 配置
→ recursive_directory_iterator 遍历
→ 有界 ThreadPool 队列
→ Worker 读取文件元数据
→ ScanStats 汇总
→ CLI/GUI/CSV/日志输出
```

## 4. 高频问题与回答

### Q1：为什么需要线程池？

目录遍历产生文件任务，线程池复用固定数量的工作线程处理文件大小和元数据，避免为每个文件创建线程带来的创建和销毁成本。线程数量由参数控制，并限制在 1～64 之间。

### Q2：为什么使用有界队列？

无界队列在大目录下可能积累大量任务，占用过多内存。有界队列达到容量后让生产者等待，形成背压，让任务生成速度和消费速度保持平衡。

### Q3：哪些数据需要同步？

文件数量、总大小和错误数使用原子变量；扩展名计数和文件元数据使用互斥锁保护；错误日志由 `ErrorLogger` 使用独立互斥锁串行写入。

### Q4：如何保证线程能够优雅退出？

主线程完成遍历后关闭线程池队列，Worker 处理完剩余任务再退出。GUI 关闭时设置取消标志，队列等待支持取消检查，避免窗口关闭时永久等待。

### Q5：为什么同时使用 `error_code` 和异常？

单个文件读取失败是可恢复错误，使用 `error_code` 记录并继续扫描；目录不存在、日志无法打开、参数非法等配置或初始化失败会抛出异常并让调用方得到明确错误。

### Q6：CSV 如何处理特殊字符？

字段包含逗号、双引号或换行时使用双引号包裹，字段内双引号写成两个双引号；文件写入 UTF-8 BOM，方便 Windows Excel 识别中文。

### Q7：线程越多是否一定越快？

不一定。线程过多会增加上下文切换、锁竞争和磁盘访问竞争。基准脚本比较 1、2、4、8 线程，但小目录数据会受到启动耗时和缓存影响，只能用于观察趋势，不能当作绝对性能结论。

### Q8：CLI 和 GUI 如何避免逻辑重复？

两者都构造 `ScanOptions` 并调用 `scan_directory`。CLI 负责参数和文本输出，GUI 负责控件、后台线程和界面展示，扫描核心保持一致。

### Q9：如何验证项目不是“只能跑通一次”？

使用 `tests/smoke_tests.ps1` 自动验证基础扫描、1/4/64 线程结果、空目录、非法目录、CSV、日志、参数错误、性能脚本和 GUI 启动；最近一次结果为 8 项通过、0 项失败。

## 5. 面试中的诚实表述

- 这是一个完整的个人练习和实习展示项目，重点是 C++ 并发、文件系统和工程化流程，不把它表述成商业生产系统。
- 当前性能样本目录较小，性能数据主要用于验证脚本和解释线程取舍，后续可以增加可控规模的测试数据和压力测试。
- 当前 GUI 使用 Win32 原生 API，后续可以增加 CSV 导出按钮、修改时间过滤和跨平台 GUI。
